# Prompt / guia de migracion de base de datos - Turnos App

Usa este documento para pedir o ejecutar una migracion de base de datos de Turnos App hacia otro proyecto Supabase/PostgreSQL. El objetivo es que la base nueva quede lista para correr la aplicacion sin reconstruir manualmente tablas, constraints, funciones, policies ni permisos.

## Objetivo

Migrar o recrear toda la estructura de base de datos necesaria para Turnos App, incluyendo:

- extensiones PostgreSQL;
- tipos enum;
- funciones helper;
- tablas principales;
- columnas y defaults;
- primary keys, foreign keys, checks e indices;
- exclusion constraints para evitar solapamientos;
- triggers;
- funciones RPC;
- grants;
- RLS y policies;
- bootstrap de perfil administrador;
- notas de validacion posterior.

El archivo principal para base nueva desde cero es:

```text
database/000_full_schema_migration.sql
```

El archivo incremental historico usado durante desarrollo es:

```text
database/001_profiles_internal_access.sql
```

Para una base nueva, usar `000_full_schema_migration.sql`. El archivo `001_profiles_internal_access.sql` queda como referencia de evolucion, no como primera opcion de migracion desde cero.

## Stack destino

- Supabase PostgreSQL.
- Supabase Auth habilitado.
- OAuth Google configurado para clientes y admin autenticado.
- Esquema `public` para tablas de aplicacion.
- Esquema `extensions` para `pgcrypto` y `btree_gist`.

## Semantica de fechas obligatoria

La aplicacion usa horarios locales y debe conservarlos sin drift UTC.

- `bookings.start_at`, `bookings.end_at`, `employee_blocks.start_at` y `employee_blocks.end_at` son `timestamp without time zone`.
- El frontend guarda strings locales `YYYY-MM-DD HH:mm:ss`.
- No convertir estos campos con `toISOString()`.
- Las constraints usan `tsrange(start_at, end_at, '[)')`.

## Tablas que deben existir

### `public.employees`

Empleados que atienden turnos.

Columnas principales:
- `id uuid primary key default gen_random_uuid()`
- `name text not null`
- `code text`
- `active boolean default true`
- `created_at timestamp without time zone default now()`
- `updated_at timestamp without time zone default now()`

Reglas:
- `employees_name_not_blank_chk`
- indice unico parcial `employees_code_uidx` sobre `code` no vacio.

### `public.services`

Actividades/servicios configurables.

Columnas principales:
- `id bigint generated by default as identity primary key`
- `name text not null`
- `icon text`
- `color text default '#42A5F5'`
- `default_duration integer default 30`
- `active boolean default true`
- `name_normalized text`
- `created_at`, `updated_at`

Reglas:
- `services_name_not_blank_chk`
- `services_default_duration_chk`
- `services_name_normalized_chk`
- indice unico `services_name_normalized_uidx`
- trigger `set_service_name_normalized_before_write`

### `public.employee_services`

Relacion N a N entre empleados y servicios.

Columnas:
- `employee_id uuid references public.employees(id) on delete cascade`
- `service_id bigint references public.services(id) on delete cascade`
- `created_at timestamp without time zone default now()`

Reglas:
- primary key `(employee_id, service_id)`
- indice `employee_services_service_idx`

### `public.bookings`

Turnos/reservas.

Columnas principales:
- `id uuid primary key default gen_random_uuid()`
- `user_id uuid references auth.users(id) on delete set null`
- `user_email text`
- `customer_name text`
- `service bigint references public.services(id) on delete restrict`
- `employee_id uuid references public.employees(id) on delete restrict`
- `start_at timestamp without time zone not null`
- `end_at timestamp without time zone not null`
- `status text default 'confirmed'`
- `created_at`, `updated_at`

Reglas:
- `bookings_valid_range_chk`: `end_at > start_at`
- `bookings_status_chk`: `reserved`, `confirmed`, `cancelled`
- `bookings_employee_no_active_overlap_excl`: evita que un empleado tenga turnos activos superpuestos.
- `bookings_user_no_active_overlap_excl`: evita que un usuario Auth tenga turnos activos superpuestos.
- `bookings_customer_email_no_active_overlap_excl`: evita que un mismo email tenga turnos activos superpuestos, incluso si el turno fue creado por admin/empleado.

Indices:
- `bookings_employee_range_idx`
- `bookings_user_idx`
- `bookings_status_idx`

### `public.employee_blocks`

Bloqueos/no disponibilidad de empleados.

Columnas principales:
- `id uuid primary key default gen_random_uuid()`
- `employee_id uuid references public.employees(id) on delete cascade`
- `start_at timestamp without time zone not null`
- `end_at timestamp without time zone not null`
- `reason text`
- `created_at`, `updated_at`

Reglas:
- `employee_blocks_valid_range_chk`: `end_at > start_at`
- `employee_blocks_employee_no_overlap_excl`: evita bloqueos superpuestos del mismo empleado.

### `public.profiles`

Perfil de usuarios Supabase Auth.

Columnas principales:
- `id uuid primary key default gen_random_uuid()`
- `user_id uuid unique references auth.users(id) on delete cascade`
- `role public.app_role default 'client'`
- `display_name text`
- `email text`
- `employee_id uuid references public.employees(id) on delete set null`
- `active boolean default true`
- `created_at`, `updated_at`

Reglas:
- `profiles_employee_role_link_chk`: si `role = 'employee'`, debe tener `employee_id`.

### `public.internal_accounts`

Cuentas internas para empleado/admin por nombre y password.

Columnas principales:
- `id uuid primary key default gen_random_uuid()`
- `role public.app_role`
- `display_name text`
- `username_normalized text`
- `password_hash text`
- `employee_id uuid references public.employees(id) on delete set null`
- `active boolean default true`
- `last_login_at timestamp without time zone`
- `created_at`, `updated_at`

Reglas:
- solo roles `admin` y `employee`.
- username normalizado igual a `normalize_text(display_name)`.
- password hash largo mayor a 20.
- employee interno requiere `employee_id`; admin interno no.
- indice unico `internal_accounts_role_username_uidx`.

### `public.internal_registration_requests`

Solicitudes de alta interna pendientes de aprobacion.

Columnas principales:
- `id uuid primary key default gen_random_uuid()`
- `role public.app_role`
- `display_name text`
- `username_normalized text`
- `password_hash text`
- `employee_id uuid references public.employees(id) on delete set null`
- `status text default 'pending'`
- `reviewed_by uuid references auth.users(id) on delete set null`
- `reviewed_at timestamp without time zone`
- `created_at timestamp without time zone default now()`

Reglas:
- roles internos `admin` y `employee`.
- statuses `pending`, `approved`, `rejected`.
- password hash no plano.

## Tipo enum requerido

```sql
public.app_role as enum ('admin', 'client', 'employee')
```

## Extensiones requeridas

```sql
create schema if not exists extensions;
create extension if not exists pgcrypto with schema extensions;
create extension if not exists btree_gist with schema extensions;
```

Uso:
- `pgcrypto`: hashes internos con `extensions.crypt` y `extensions.gen_salt('bf')`.
- `btree_gist`: exclusion constraints con igualdad sobre uuid/text y rango temporal.

## Funciones helper requeridas

- `public.normalize_text(value text)`: normaliza nombres/emails/servicios para comparacion sin acentos, mayusculas ni espacios duplicados.
- `public.set_updated_at()`: mantiene `updated_at` en updates.
- `public.set_service_name_normalized()`: mantiene `services.name_normalized`.
- `public.handle_new_auth_user()`: crea/actualiza `profiles` al insertar en `auth.users`.
- `public.current_user_role()`: devuelve rol del usuario Auth actual.
- `public.is_admin()`: true si el perfil Auth actual es admin activo.
- `public.is_employee_for(employee_id_value uuid)`: true si el usuario Auth actual es empleado vinculado a ese empleado.

## RPCs requeridas para acceso interno

- `public.request_internal_registration(account_role, display_name_value, password_value, employee_id_value)`
  - Publica para `anon` y `authenticated`.
  - Crea solicitud pendiente con password hasheada.

- `public.verify_internal_login(account_role, display_name_value, password_value)`
  - Publica para `anon` y `authenticated`.
  - Verifica password contra `extensions.crypt`.
  - Devuelve `id`, `role`, `display_name`, `employee_id`.

- `public.list_internal_registration_requests(status_value)`
  - Solo admin Auth.
  - Lista solicitudes para aprobacion.

- `public.approve_internal_registration(request_id_value, employee_id_value)`
  - Solo admin Auth.
  - Crea cuenta interna y, si corresponde, empleado.

- `public.reject_internal_registration(request_id_value)`
  - Solo admin Auth.

- `public.register_internal_account(account_role, display_name_value, password_value, employee_id_value)`
  - Solo admin Auth.
  - Crea cuenta interna directa.

## RPCs requeridas para bloqueos de empleado interno

Estas son necesarias porque el login interno no es una sesion real de Supabase Auth y no satisface RLS con `auth.uid()`.

- `public.list_internal_employee_blocks(account_id_value)` devuelve `jsonb`.
- `public.create_internal_employee_block(account_id_value, start_at_value, end_at_value, reason_value)` devuelve `jsonb`.
- `public.update_internal_employee_block(account_id_value, block_id_value text, start_at_value, end_at_value, reason_value)` devuelve `jsonb`.
- `public.delete_internal_employee_block(account_id_value, block_id_value text)` devuelve `void`.

Estas funciones validan:
- cuenta interna activa;
- rol employee;
- `employee_id` vinculado;
- rango valido;
- no crear/mover bloqueos al pasado;
- no solapar bloqueos del mismo empleado.

## Triggers requeridos

- `on_auth_user_created` sobre `auth.users` despues de insert, ejecuta `public.handle_new_auth_user()`.
- `set_service_name_normalized_before_write` sobre `public.services` antes de insert/update de `name`.
- `employees_set_updated_at`.
- `services_set_updated_at`.
- `bookings_set_updated_at`.
- `employee_blocks_set_updated_at`.
- `profiles_set_updated_at`.
- `internal_accounts_set_updated_at`.

## Grants requeridos

Roles `anon` y `authenticated`:
- usage en schema `public`.
- usage en schema `extensions`.

Role `authenticated`:
- `select, insert, update` en `profiles`.
- `select, insert, update, delete` en `bookings`.
- `select, insert, update, delete` en `services`.
- `select, insert, update, delete` en `employees`.
- `select, insert, delete` en `employee_services`.
- `select, insert, update, delete` en `employee_blocks`.
- usage/select sobre sequences de `public`.

Tablas internas:
- `revoke all on public.internal_accounts from anon, authenticated`.
- `revoke all on public.internal_registration_requests from anon, authenticated`.
- acceso solo via RPCs `security definer`.

RPCs publicas:
- `request_internal_registration`: `anon`, `authenticated`.
- `verify_internal_login`: `anon`, `authenticated`.
- RPCs de bloqueos internos: `anon`, `authenticated`.

RPCs administrativas:
- `register_internal_account`, `list_internal_registration_requests`, `approve_internal_registration`, `reject_internal_registration`: `authenticated`, con validacion interna `public.is_admin()`.

## RLS y policies requeridas

RLS habilitado en:
- `profiles`
- `internal_accounts`
- `internal_registration_requests`
- `bookings`
- `services`
- `employees`
- `employee_services`
- `employee_blocks`

Policies principales:

### Profiles

- `profiles_select_own_or_admin`: usuario ve su perfil o admin ve todos.
- `profiles_update_own_basic_or_admin`: usuario actualiza basico propio sin cambiar rol; admin puede actualizar.
- `profiles_admin_insert`: solo admin.

### Internal tables

- `internal_accounts_no_direct_select`: `using false`.
- `internal_registration_requests_no_direct_select`: `using false`.

### Services

- `services_authenticated_read`: authenticated lee todos.
- `services_admin_insert`: solo admin.
- `services_admin_update`: solo admin.
- `services_admin_delete`: solo admin.

### Employees

- `employees_authenticated_read`: authenticated lee todos.
- `employees_admin_insert`: solo admin.
- `employees_admin_update`: solo admin.
- `employees_admin_delete`: solo admin.

### Employee services

- `employee_services_authenticated_read`: authenticated lee todos.
- `employee_services_admin_insert`: solo admin.
- `employee_services_admin_delete`: solo admin.

### Bookings

- `bookings_authenticated_read`: authenticated lee todos para disponibilidad de agenda.
- `bookings_clients_insert_own_or_admin`: admin, empleado Auth vinculado o cliente propio.
- `bookings_update_own_future_or_admin`: admin, empleado Auth vinculado o cliente propietario futuro.
- `bookings_delete_own_future_or_admin`: admin, empleado Auth vinculado o cliente propietario futuro.

### Employee blocks

- `employee_blocks_authenticated_read`: authenticated lee todos para disponibilidad.
- `employee_blocks_admin_insert`: admin o empleado Auth vinculado.
- `employee_blocks_admin_update`: admin o empleado Auth vinculado.
- `employee_blocks_admin_delete`: admin o empleado Auth vinculado.

## Orden recomendado de migracion en Supabase

1. Crear un proyecto Supabase nuevo.
2. Configurar Auth provider Google en Supabase.
3. Abrir SQL Editor.
4. Ejecutar completo `database/000_full_schema_migration.sql`.
5. Verificar que no haya errores por extensions, constraints o policies.
6. Levantar la app apuntando al nuevo `supabaseUrl` y `supabaseKey` en `src/api/supabaseClient.js`.
7. Iniciar sesion una vez con Google usando la cuenta que sera admin.
8. Promover esa cuenta a admin:

```sql
update public.profiles
set role = 'admin', updated_at = now()
where email = 'tu-email@gmail.com';
```

9. Desde la app admin:
   - crear actividades;
   - crear empleados;
   - asignar actividades a empleados;
   - crear bloqueos si corresponde;
   - aprobar solicitudes internas.

## Validaciones post-migracion

Ejecutar estas consultas en SQL Editor para confirmar estructura basica:

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name in (
    'employees',
    'services',
    'employee_services',
    'bookings',
    'employee_blocks',
    'profiles',
    'internal_accounts',
    'internal_registration_requests'
  )
order by table_name;
```

```sql
select typname
from pg_type
where typname = 'app_role';
```

```sql
select conname
from pg_constraint
where conname in (
  'bookings_employee_no_active_overlap_excl',
  'bookings_user_no_active_overlap_excl',
  'bookings_customer_email_no_active_overlap_excl',
  'employee_blocks_employee_no_overlap_excl'
)
order by conname;
```

```sql
select tablename, policyname
from pg_policies
where schemaname = 'public'
order by tablename, policyname;
```

```sql
select proname
from pg_proc
join pg_namespace on pg_namespace.oid = pg_proc.pronamespace
where nspname = 'public'
  and proname in (
    'normalize_text',
    'handle_new_auth_user',
    'request_internal_registration',
    'verify_internal_login',
    'approve_internal_registration',
    'list_internal_employee_blocks',
    'create_internal_employee_block',
    'update_internal_employee_block',
    'delete_internal_employee_block'
  )
order by proname;
```

## Pruebas funcionales minimas despues de migrar

1. Login Google como cliente.
2. Verificar que se crea fila en `profiles` con rol `client`.
3. Promover una cuenta a `admin`.
4. Entrar como admin.
5. Crear al menos una actividad con icono, color y duracion.
6. Crear al menos un empleado.
7. Asignar la actividad al empleado.
8. Crear un turno desde cliente.
9. Intentar crear otro turno superpuesto para el mismo empleado: debe fallar.
10. Intentar crear otro turno superpuesto para el mismo cliente/email: debe fallar.
11. Crear bloqueo de empleado.
12. Intentar reservar dentro del bloqueo: debe fallar.
13. Registrar cuenta interna de empleado.
14. Aprobar solicitud desde admin.
15. Login interno empleado.
16. Crear/editar/eliminar bloqueo propio.
17. En celular, probar cancelar turno desde la grilla y confirmar que no abre seleccion nueva.

## Datos que no migra automaticamente este SQL

`database/000_full_schema_migration.sql` crea estructura, permisos y logica. No migra datos existentes de otra base.

Si se necesita migrar datos reales, exportar e importar en este orden para respetar foreign keys:

1. `employees`
2. `services`
3. `employee_services`
4. `profiles` despues de tener usuarios en `auth.users`
5. `bookings`
6. `employee_blocks`
7. `internal_accounts` si realmente se desean conservar hashes internos
8. `internal_registration_requests` si se desea conservar historico

Advertencia sobre `auth.users`:
- Supabase Auth no se debe copiar manualmente como una tabla comun sin entender el impacto.
- Lo mas simple para un entorno nuevo es que los usuarios vuelvan a iniciar sesion y se reconstruyan perfiles por trigger.
- Para migraciones productivas con usuarios reales, usar herramientas oficiales de Supabase/Auth o planificar una migracion especifica.

## Riesgos y notas importantes

- Las sesiones internas actuales viven en `sessionStorage`; no son sesiones Supabase Auth.
- Las escrituras directas protegidas por `auth.uid()` funcionan para usuarios Auth, no para sesiones internas puras.
- Por eso existen RPCs `security definer` para bloqueos internos de empleados.
- Si en el futuro se quiere que admin interno maneje todo sin Google/Auth, crear RPCs administrativas para ABM y reservas.
- Las exclusion constraints pueden fallar si se importan datos con solapamientos. Limpiar conflictos antes de aplicar constraints o importar datos ya saneados.
- Mantener `extensions.crypt` y `extensions.gen_salt`, no `crypt` sin schema, porque en Supabase puede depender del `search_path`.

## Prompt corto para otro asistente

Necesito migrar/recrear la base de datos de Turnos App en un nuevo Supabase. Usa `database/000_full_schema_migration.sql` como fuente principal. Debe incluir extensiones `pgcrypto` y `btree_gist`, enum `app_role`, tablas `employees`, `services`, `employee_services`, `bookings`, `employee_blocks`, `profiles`, `internal_accounts`, `internal_registration_requests`, triggers, funciones helper, RPCs internas, grants, RLS policies y exclusion constraints contra solapamientos de empleados, usuarios, emails de clientes y bloqueos. Mantener `timestamp without time zone` y formato local para horarios. Despues de ejecutar, configurar Google OAuth, hacer login con la cuenta admin y promoverla en `profiles` con rol `admin`. Validar con consultas a tablas, constraints, policies y RPCs, y probar alta de actividad, empleado, reserva, bloqueo, login interno y cancelacion movil.
